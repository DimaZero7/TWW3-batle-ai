# Устройство моста и слои

[← Назад](README.md) · [Документация](../README.md)

Код разбит на **приложения** по предметным областям, логика живёт в
**сервисах**, а точки входа только связывают их между собой. Так устроен
photo-fixing — другой проект автора, веб-приложение на Python; ниже его файлы
приводятся для сравнения. Главное отличие: код работает внутри игры
(Lua 5.1 в WH3), поэтому обращения к движку собраны в отдельном слое —
**адаптерах**.

## Папки

```text
bridge/
├── lua/
│   ├── apps/          приложения: core, battle, map, navigation, units, orders, telemetry, bridge, mem
│   └── entries/       точки входа: nn_arena, charge_probe, missile_probe, morale_probe, map_capture, move_probe
├── scenarios/         XML-сценарии боёв
├── build.py           сборка pack: python -m bridge.build <цель>
├── pack/              формат PFH5, бандлер Lua-модулей, таблицы правил игры для --kv
├── launcher/          установка pack, запуск WH3, ожидание, очистка, чтение JSONL
├── companion/         помощник в Docker: стратег, цепочка, входы уровней, файлы обмена
├── config/            default.json в git, local.json — настройки машины; True Sight, memreader, планы move-probe
├── tests/             дымовой тест моста
└── docs/              эта документация
```

Соседи: `sim/` — симулятор (файл боя арены `sim/arena.py`, армии, снятые карты `sim/maps/`), `net/` — уровни сети и
их веса, `game/` — запуск боёв, пробы и разметка (зовут сборку и launcher моста), `contract/` — сверка «вход симулятора
= мост» ([паритет](../../../contract/parity.md)), `reverse/` — разбор игры и места памяти для `--mem`
([reverse](../../../reverse/README.md)). Вне git: `build/` (паки и прогоны), `state/` (метки `HUMAN_PLAYING`,
`probe_game.lock`), `tmp/`.

## Слои приложения

Каждое приложение — папка `bridge/lua/apps/<имя>/` с файлами по ролям:

| Файл | Аналог в photo-fixing | Правило |
|---|---|---|
| `*adapter.lua` | `models.py` | **Единственное место**, где вызываются `bm`, объекты отрядов, `common` (CCO). Возвращает обычные таблицы |
| `services.lua` и другие чистые модули (`orders/facing.lua`, `battle/screen_proj.lua`, `core/*`) | `services.py` | Чистая логика над обычными таблицами. Без движка, без файлов, без таймеров |

Не у каждого приложения есть оба слоя. Например, в `units` только адаптеры, а в
`orders` — адаптер, чистый `facing` и `planner_adapter` (отряды ИИ игры).

**Точки входа** (`bridge/lua/entries/`) — аналог `router.py`: подписываются на фазы
боя, запускают тик, вызывают адаптеры и сервисы и пишут телеметрию. Логики
решений в них нет.

## Правила зависимостей

```text
entries                         →  любые apps
bridge                          →  core, orders, telemetry.adapter, battle.winds
battle (разметка вживую)        →  core, bridge.exchange_adapter, bridge.services
telemetry.observer_adapter      →  core, units, bridge.services
navigation                      →  core, map.adapter (построение вектора)
map, units, telemetry.adapter   →  core
mem                             →  только mem
orders                          →  только свой facing
battle.adapter, services        →  ничего
core                            →  ничего
```

- Приложения не знают о точках входа; `core` ничего не импортирует из
  приложений.
- Сервисы не импортируют адаптеры. Если сервису нужен движок, его передают
  колбэком: `map.services.build_frame(query)` получает запрос к радару от
  `map.adapter`, а без игры передают обычную функцию.
- Модули подключаются обычным `require('apps.map.services')`. Сборщик кладёт
  все модули в один скрипт и подставляет свой загрузчик
  ([сборка](../launch/build.md)); циклический `require` — ошибка сборки.
- Чистый код не трогает движок, ключи отрядов (`wh_…`) не зашиты в логику, модуль не длиннее 1000 строк.

## Поток данных в бою

```text
XML-сценарий  →  WH3 загружает бой и наш скрипт из pack
  →  entry: проверка типа боя и чтение сторон и ролей (battle)
  →  фаза Deployment: проба ставит свои отряды (orders.teleport), стратег помощника ставит нашу сторону
     (bridge.deploy_adapter) или расстановка остаётся файлу боя / человеку
  →  фаза Deployed: скорость (battle.speed_guard), срок (battle.deadline), тик раз в tick_ms:
        map / units / mem (пробы)        →  показания
        bridge  ↔  помощник (файлы)      →  приказы цепочки нашим отрядам (orders.adapter)
        orders.adapter                   →  приказы по плану пробы
        telemetry                        →  events.jsonl
  →  result (исход, застой, тайм-аут, срок), очистка колбэков
  →  launcher копирует результаты в build/<цель>/runs/<время>/
```

## Правила моста

| Правило | Где описано |
|---|---|
| Все бои запускаются с модом True Sight (Workshop 3628832922) | [запуск боя](../launch/run.md#обязательный-мод-true-sight) |
| Бои против ИИ игры — только на нормальной сложности; в игре — только RTX | [честная сложность](../launch/run.md#честная-сложность), [графика](../launch/run.md#графика) |
| Игру не запускаем, пока играет пользователь (`state/HUMAN_PLAYING`) или игру держит чужой замок (`state/probe_game.lock`) | [запуск боя](../launch/run.md) |
| Сеть получает в игре то же, что в симуляторе: игра пишет всё, вход помощника прячет то, чего не видит человек; новое поле входа — симулятор, мост и строка таблицы паритета вместе | [паритет](../../../contract/parity.md), [bridge](../apps/bridge.md#вход-сети-отряда-один-в-один-с-симулятором) |
| memreader Plus — только в пробах, никогда в бою сети | [memreader](../apps/memreader.md#границы) |
| Бой всегда заканчивается сам: срок по реальному времени, застой без урона 10 игровых минут, лимит launcher | [точки входа](../apps/entries.md#общее) |
| Скорость держится на заданной и после решения исхода (кроме боя человека с `--free-speed`) | [battle](../apps/battle.md) |
| Приказы — только проверенными вызовами движка | [orders](../apps/orders.md) |

## Как добавить приложение

1. Создать `bridge/lua/apps/<имя>/` и разделить код: вызовы движка — в `adapter.lua`,
   логику — в `services.lua`.
2. Подключить его `require` из точки входа: в пак попадает только то, до чего дотягиваются `require`; сборка
   проверяет синтаксис Lua. Дымовой тест — `bridge/tests/test_bridge_smoke.py`.
3. Описать приложение в `bridge/docs/apps/<имя>.md`, добавить строку в [список приложений](apps.md) и в
   [оглавление модулей](../apps/README.md).
