# Устройство проекта и слои

[← Назад](README.md) · [Документация](../README.md) · [English](../../en/architecture/overview.md)

Код разбит на **приложения** по предметным областям, логика живёт в
**сервисах**, а точки входа только связывают их между собой. Так устроен
photo-fixing — другой проект автора, веб-приложение на Python; ниже его файлы
приводятся для сравнения. Главное отличие: код работает внутри игры
(Lua 5.1 в WH3), поэтому обращения к движку собраны в отдельном слое —
**адаптерах**.

## Папки

```text
src/
├── apps/              приложения: core, battle, map, navigation, units, intel,
│                      observation, orders, telemetry
└── entries/           точки входа: ai_vs_ai, archer_range, enemy_layout, manual_record,
                       map_capture, move_probe, nn_arena, roster_capture, unit_readout
scenarios/             XML-сценарии боёв
tools/                 Python/PowerShell вне игры
├── build.py           сборка pack: python -m tools.build <цель>
├── pack/              формат PFH5 и бандлер Lua-модулей
├── launcher/          установка pack, запуск WH3, ожидание, очистка
├── telemetry/         чтение JSONL, пока игра пишет
├── analysis/          карты высот, склоны, проходы, разборы прогонов
├── nn/                правила из базы игры, сценарий арены, записи арены как массивы
└── docs/              оглавления хабов документации
tests/                 pytest + lupa: тот же Lua 5.1 без игры
config/                default.json в Git, local.json — настройки машины
data/                  компактные проверенные данные по картам и отрядам
docs/ru, docs/en       документация на двух языках
research/              архив исследований: доказательства, зонды, старые скрипты
```

## Слои приложения

Каждое приложение — папка `src/apps/<имя>/` с файлами по ролям:

| Файл | Аналог в photo-fixing | Правило |
|---|---|---|
| `*adapter.lua` | `models.py` | **Единственное место**, где вызываются `bm`, объекты отрядов, `common` (CCO). Возвращает обычные таблицы |
| `services.lua` и другие чистые модули (`orders/facing.lua`, `core/*`) | `services.py` | Чистая логика над обычными таблицами. Без движка, без файлов, без таймеров |

Не у каждого приложения есть оба слоя. Например, в `units` только адаптеры, а в
`intel` — адаптер и сервис памяти.

**Точки входа** (`src/entries/`) — аналог `router.py`: подписываются на фазы
боя, запускают тик, вызывают адаптеры и сервисы и пишут телеметрию. Логики
решений в них нет.

## Правила зависимостей

```text
entries                         →  любые apps
observation                     →  units, intel (их адаптеры)
navigation                      →  core, map.adapter (построение вектора)
intel, map, telemetry, units    →  core
orders                          →  только свой facing
battle                          →  ничего
core                            →  ничего
```

- Приложения не знают о точках входа; `core` ничего не импортирует из
  приложений. В photo-fixing `common` знал о `auth` и `routes` — здесь так
  делать нельзя.
- Сервисы не импортируют адаптеры. Если сервису нужен движок, его передают
  колбэком: `map.services.build_frame(query)` получает запрос к радару от
  `map.adapter`, а тесты передают обычную функцию.
- Модули подключаются обычным `require('apps.map.services')`. Сборщик кладёт
  все модули в один скрипт и подставляет свой загрузчик
  ([сборка](../launch/build.md)); циклический `require` — ошибка сборки.
- У каждого приложения есть уровень в `tools/architecture.py`. Сейчас все —
  основа (0); будущий уровень выше может пользоваться основой, но не наоборот.
- Тесты `tests/architecture/` следят за уровнями, а ещё что чистый код не трогает
  движок, ключи отрядов (`wh_…`) не зашиты в логику и модуль не длиннее 1000 строк.

## Поток данных в бою

```text
XML-сценарий  →  WH3 загружает бой и наш скрипт из pack
  →  entry: проверка типа боя и чтение сторон и ролей (battle)
  →  фаза Deployment: зонд ставит свои отряды (orders.teleport) или оставляет расстановку игре
  →  фаза Deployed: скорость (battle.speed_guard), срок (battle.deadline), тик раз в tick_ms:
        units / intel / observation / map    →  показания
        orders.adapter, orders.planner_adapter  →  приказы по плану зонда или штатному ИИ
        telemetry                            →  events.jsonl
  →  result (исход, застой, тайм-аут, срок), очистка колбэков
  →  launcher копирует результаты в build/<цель>/runs/<время>/
```

## Правила проекта

| Правило | Где описано |
|---|---|
| Все бои запускаются с модом True Sight (Workshop 3628832922) | [запуск боя](../launch/run.md#обязательный-мод-true-sight) |
| Бои против ИИ игры — только на нормальной сложности | [честная сложность](../launch/run.md#честная-сложность) |
| ИИ стороны получает только **сводку своей стороны**: свои отряды целиком, о врагах — видимость, позиция пока виден, последняя известная позиция. Полная сводка — только эталон и данные для исследования | [observation](../apps/observation.md) |
| Скрытые отряды не должны раскрываться: проверяется отчётом `--view side` | [видимость](../game/units/visibility.md) |
| Бой всегда заканчивается сам: срок по реальному времени, застой без урона 10 игровых минут, лимит launcher | [точки входа](../apps/entries.md) |
| Скорость держится на заданной (×20) и после решения исхода | [battle](../apps/battle.md) |
| Приказы — только проверенными вызовами движка | [orders](../apps/orders.md) |
| Что собирать в прогоне — выбирается профилем из каталога показателей | [каталог показателей](../game/readouts.md) |

## Как добавить приложение

1. Создать `src/apps/<имя>/` и разделить код: вызовы движка — в `adapter.lua`,
   логику — в `services.lua`.
2. Написать тесты в `tests/apps/<имя>/`. Сервисы тестируются напрямую,
   адаптеры — на поддельных объектах движка.
3. Описать приложение в `docs/ru/apps/<имя>.md` и `docs/en/apps/<имя>.md`,
   добавить строку в [список приложений](apps.md) и обновить оглавления
   (`python -m tools.docs.index_doc`).
