# Чтение памяти игры в пробах (memreader Plus)

[← Назад](README.md) · [Документация](../README.md) › [Знания об игре](README.md) › Чтение памяти игры

Мод memreader Plus (мастерская 3811098873, автор Druwski, исходник github.com/PKozdra/memreader_plus) даёт скрипту Lua
читать память игры и перехватывать её функции. Мы подключаем его **только в пробах**, чтобы видеть то, чего скрипт игры
не отдаёт: снаряды в полёте и бойцов отряда (место, состояние, таймер удара, цель, взгляд, здоровье, натиск).

## Границы

- Только пробы (`tools.build <проба> --mem`: `missile-probe` — снаряды, `charge-probe` — бойцы). В бой сети (`nn_arena`), в экзамены и в обычный запуск игры мод мы не
  ставим. Не во время игры пользователя (`build/steps/HUMAN_PLAYING`, замок `build/steps/probe_game.lock`).
- Только чтение и два перехвата, которые ничего не меняют: они считают вызовы и читают память, функция игры
  выполняется как обычно. В память ничего не пишется, сетевые функции не трогаются.
- **Адреса функций, байтовые сигнатуры и смещения структур — не в git.** Они в `build/mem/sites.json` (папка `build`
  в git не идёт); разбор программы — в R-work (`notes/mem/projectiles.md`). Код проекта знает только имена: места
  `proj_update`, `ammo_left`, `battle_ref`, `battle_global`, поля `mgr_active`, `p_*` (снаряд), `s_feet`, `r_category`,
  `b_world`, `w_battle`, `w_proj`, `i_unit`, `u_ammo`, `u_battle`; для бойцов место `dir_table` и поля `u_men`, `w_tick`,
  `m_*` (боец). Сборка кладёт их в настройки пробы (пак тоже в
  `build/`); Lua сам файл не читает: `io.open` в Lua 5.1 не открывает путь с кириллицей.
- Пак мода закреплён по SHA-256 (`config/memreader.json`): после обновления мода сборка откажет, пока его не проверят.

## Как устроено

| часть | где | что делает |
|---|---|---|
| закрепление пака | `config/memreader.json` | мастерская, имя пака, SHA-256, где лежит файл мест |
| файл мест (вне git) | `build/mem/sites.json` (или `BAI_MEM_SITES`) | адрес места, ожидаемые байты, сигнатура, смещения полей, SHA-256 `Warhammer3.exe` |
| сборка | `tools/build.py --mem`, `tools/mem_sites.py` | кладёт memreader рядом с нашим паком (launcher копирует его в `data/` и убирает после боя), места — в настройки пробы; другой `Warhammer3.exe` — отказ |
| Lua | `src/apps/mem/projectiles.lua` | проверки (мод загружен, байты места совпали, сигнатура нашлась ровно один раз на том же адресе), перехваты, путь к списку снарядов, разбор списка |
| Lua | `src/apps/mem/entities.lua` | бойцы отряда: привязка скриптового отряда к боевому, чтение всех бойцов, поиск указателей на врага |
| проба | `src/entries/missile_probe.lua` (`config.mem`) | опрос списка каждые 100 мс боя; строки `mem_attach` (проверки) и `mem_proj` (каждый тик пробы, 0,5 с) в записи боя |
| проба | `src/entries/charge_probe.lua` (`config.mem`) | бойцы атакующего и цели каждой дорожки раз в 100 мс боя (`mem_men`); план `memmelee` — рукопашная пехоты по бойцам |
| разбор | `python -m tools.nn.mem_probe [папки]` | память против скрипта: снаряды каждой дорожки против расхода боезапаса |
| разбор | `python -m tools.nn.mem_probe --men [папки]` | бойцы из памяти против скрипта: живые и место отряда в каждом опросе |

Числа Lua в игре — 32-битные: целые больше 16 777 216 теряют точность. Поэтому адрес места сборка делит на две точные
части (`hi × 2²⁰ + lo`).

## Снаряды в полёте

**Где лежат.** Игра держит все снаряды боя в одном списке менеджера снарядов. Раз в такт симуляции его обновляет одна
функция (место `proj_update`). Путь к менеджеру: отряд боя → бой → мир боя → менеджер; проверка пути — мир ссылается
обратно на тот же бой.

**Почему опрос, а не перехват.** Симуляция боя идёт **в своём потоке**, не в потоке скрипта. memreader пускает в
обработчик Lua только вызовы из потока скрипта (Lua однопоточный), остальные проходят мимо: перехват `proj_update`
ставится, но за бой 2213 вызовов — все из потока симуляции, обработчик не вызван ни разу. Поэтому список снарядов
читает сама проба, своим таймером раз в 100 мс боя (поток скрипта, между тактами).

**Перехват, который работает** — `unit:ammo_left()` скрипта (место `ammo_left`, поток скрипта). Это функция-обёртка
скрипта: она проверяет аргументы вызова Lua, поэтому функцию игры нельзя звать из обработчика (`hook_next` даёт
ошибку `bad argument #1 to 'hook_next' (expecting zero arguments)`, memreader снимает перехват). Ставим его как
«префикс» (`patcher:prefix`): обработчик только читает, функцию игры memreader зовёт сам. Обработчик берёт из
аргумента отряд боя и читает его боезапас из памяти; заодно отряд даёт путь к бою.

**Что пишется** (номер опроса `c`):

- **появился** `{id, c, st, x, y, z, vx, vy, vz, t, rec, sx, sy, sz}` — точка (y — вверх, высота над уровнем карты),
  скорость, время полёта, запись базы снаряда (номер), ноги стрелявшего бойца;
- **сменил состояние** `{id, c, st, x, y, z, t}`;
- **ушёл из списка** `{id, c}` — после трёх опросов подряд без него (опрос идёт параллельно с потоком симуляции);
- раз в тик пробы — список летящих сейчас (до 300).

**Жизнь объекта в списке**: выпущенный снаряд появляется в состоянии 0 с временем полёта 0 и уходит в 7,
когда долетел; там, где он упал, игра ставит **новый** объект «лежит на земле» (первое состояние 6, живёт ~20 с);
попавший в бойца — тоже новый объект (2 → 3 → 7, стрелок сохранён). Разбор (`tools/nn/mem_probe.py`) считает
выпущенными только объекты, появившиеся в состоянии 0.

Как запускать:

```
python -m tools.build missile-probe --mprobe-plan dist --mprobe-battle 2 --mem   # сборка
python -m tools.nn.missile_probe run --plan dist --battles 2 --mem              # сборка + бой
python -m tools.nn.mem_probe                                                     # разбор последнего боя с памятью
```

## Что проверено

Бой: проба `dist`, бой 2 (ополченцы 50 м, пращники, ночные бегуны и лучники 80 м; 4 дорожки), ×20.

| что | итог |
|---|---|
| мод загружен, байты всех мест совпали, сигнатуры — ровно одно совпадение | да (memreader 0.15.1) |
| перехват `ammo_left` срабатывает, читает отряд и боезапас | да: 40 из 40 чтений боезапаса из памяти = значение скрипта в том же тике |
| перехват `proj_update` | ставится, 2213 вызовов за бой, все из потока симуляции (обработчик Lua не вызывается) |
| выпущено снарядов: память против расхода боезапаса скрипта | 1423 / 1423, 2473 / 2473, 1583 / 1583, 1127 / 1127 — **6606 из 6606** |
| совпадение по времени (корзины 0,5 с, ±1 корзина) | 91 % (ополченцы: пуля летит 0,6 с, опрос 0,1 с), 99 %, 99 %, 95 %; всего 96 % |
| выпущенный снаряд виден у своего стрелка | медиана 10 м от центра отряда, 90 % — до 16 м; без дорожки — 0 |
| снаряд долетел (ушёл из списка) | 100 %; время полёта: пуля 0,6 с, стрелы и камни 1,9–2,0 с; скорость вылета 90 / 49 / 49 / 44 м/с |
| где упал | медиана 9–12 м от центра цели, 68–94 % — в 15 м |
| новые объекты | 6504 «лежит на земле», 1389 «в бойце» |

### Пробовали и отказались

- **Обработчик Lua на функции симуляции** (`proj_update`): поток симуляции, обработчик не вызывается (2213 из 2213
  вызовов мимо).
- **Глобальный указатель боя** (`battle_global`, 11 мест в коде читают его поле мира): в бою поле мира пустое — это не
  тот объект. Путь к бою идёт через отряд (поле `u_battle`, найдено перебором полей отряда: указатель, у которого мир
  ссылается обратно).
- **`hook_next` в обёртке скрипта** (`ammo_left`): обёртка проверяет аргументы текущего вызова Lua, а это уже вызов
  `hook_next` — ошибка, перехват снят. Префикс патчера работает.

## Бойцы отряда

**Где лежат.** У боевого отряда — вектор указателей на бойцов (поле `u_men`); **погибшие из него уходят**, поэтому
длина вектора = число живых. Скриптовый отряд привязывается к боевому тем же перехватом `ammo_left`: проба зовёт
`unit:ammo_left()` у каждого отряда дорожек, префикс читает из аргумента боевой отряд и проверяет, что каждый боец
вектора ссылается обратно на этот отряд; потом перехват снимается — в бою ни одного перехвата. Часы — счётчик тактов
мира боя (`w_tick`, такт 0,1 с): «сейчас» таймеров бойца = такт × 0,1.

**Что читается** (строка бойца, `tools/nn/mem_probe.py` `MAN`):

| поле | что |
|---|---|
| `id` | номер бойца на весь бой (по адресу) |
| `live` | в бою (жив) |
| `x`, `z`, `y` | место ног (y — вверх) |
| `vx`, `vz` | скорость |
| `face` | взгляд: номер 0…65535; вектор (x, z) = (sin, cos) номер / 65536 оборота (таблица игры, проверена при подключении) |
| `hp` | здоровье бойца |
| `anim`, `mode` | состояние анимации; ход (0 шаг, 1 бег, 2 натиск) |
| `react` | реакция: 0xd шаг назад, 0xe отброшен, 0xf сбит, 0x10 полёт, 0x11 встаёт, 0x12 (ещё одна, ~2,2 с) |
| `mark` | таймер удара: время начала последней атаки (−100 — ещё не бил) |
| `fit` | флаги цели (бит 0x2 — годен как цель) |
| `flags`, `brace` | флаги (бит 0x8 — в упоре) и множитель упора B |
| `speed` | своя скорость |
| `tgt`, `tgt2` | цель задачи бойца (номер врага) и второй указатель на врага (смысл не установлен) |
| `carried`, `chg` | сидит ли на ком-то; срок натиска: множитель натиска = clamp((срок − сейчас) / 13 с, 0, 1) |

Пишется (`mem_men`, каждый опрос): у дорожек около касания (ближе `men_near_m` до него и до `men_after_s` после) —
каждые 0,1 с, у прочих — раз в 0,5 с; рядом — что в тот же миг отдаёт скрипт (`number_of_men_alive`, `position`). Через
1, 3, 5 с после касания — поиск указателей на врага у 12 бойцов (`mem_men_discover`; так найдена цель). Поиск читает
только поля самого бойца: первая версия шла по каждому найденному указателю ещё на шаг — после ~10⁵ таких чтений
состояние Lua в игре сломалось (бой упал).

**Проверка** (проба `cavcharge` с `--mem`, 2 боя по 3 дорожки, 453 опроса, 2540 пар «опрос × отряд»): живые из памяти
= `number_of_men_alive` в **2540 из 2540**; место отряда скрипта (`unit:position`) — всегда место одного из его бойцов
(0,00 м; это не среднее бойцов — до него 0,3–8 м); места пехоты = `ManList` скрипта до 0,0 м, у рыцарей `ManList` даёт
всадников в 0,8–1,1 м от тел. Цена: 660 бойцов за опрос — 5–7 мс процессора (до 12), такт за опрос не меняется.

**Что показали бойцы** (удар конницы; разбор `build/diag_mem/entities/`, числа — в
[симуляторе](../training/simulator.md#сверка-натиска-конницы)): сбитый лежит 2,1–2,2 с и встаёт 3,2 с — не цель ~5,3 с;
отброшенный — 2,2–2,7 с, шаг назад — 1,1 с; урон столкновения — только сбитым (0 из 31 отброшенного), при сближении
больше 7 м/с до обмена (после обмена — 0,4–4,8 м/с); передний ряд бьёт копьём до касания и снова вместе через 5,1 с;
задних в первой волне ~10, бьют цель в 1,9–3,3 м; натиск у каждого рыцаря держится, пока он сам в натиске (1,4 / 2,5 /
4,1 с после касания), и только потом спадает.

**Что показали бойцы в рукопашной пехоты** (проба `memmelee` с `--mem`, 1 бой, 4 дорожки, бойцы каждые 0,1 с весь бой;
разбор `build/diag_mem/melee/`, числа — в [симуляторе](../training/simulator.md#удар-по-бойцам-из-памяти-рукопашная-пехоты)):
удар = новое значение таймера удара; здоровье цели (поле цели бойца) падает через 0,7–1,1 с после него (рыцари 0,7, мечи 0,9,
алебарды 1,1); у 98 % потерь здоровья есть удар по этому бойцу — поле цели и есть тот, кого бьют. Урон удара — правило базы
(бронебойный + обычный за броней), не больше здоровья цели; попадает по правилу 35 + атака − защита у трёх пар из четырёх
(копейщики по штурмкрысам 0,13 при правиле 0,21); после промаха боец бьёт не раньше, чем после попадания, — раз в
1,2–1,35 интервала. Атака шагом с 3 м — натиск: все бойцы в режиме натиска (`mode` 2) на касании. Сумма потерь здоровья
бойцов = потерям отряда по скрипту (3285 = 3285, 2048 = 2048 …).

## Вход сети

У сети отряда (`tools/nn/unit/view.py`) входа по снарядам в полёте нет. У тактика два эффекта, которые ждут моста:
«под огнём артиллерии» и «попадание артиллерии» (`tools/nn/tactic/raw.py`, источник `wait`, 0 и в симуляторе, и в
игре). Чтение снарядов — готовый источник для них, но в бой сети оно не подключено (см. границы), поэтому паритет
пока не меняется: таблица `build/diag_g49/bridge_parity.md`, раздел «Снаряды из памяти».
